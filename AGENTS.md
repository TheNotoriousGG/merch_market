# Правила работы с backend Амра Шоп

Перед любым действием прочитай полностью:

1. `docs/ENGINEERING_CHARTER.md`
2. `docs/DECISION_REGISTER.md`
3. `docs/IMPLEMENTATION_PLAN.md`
4. `docs/PROJECT_STATUS.md`
5. этот файл

## Стоп-условия

- Не начинай новый этап, пока предыдущий gate не закрыт и `PROJECT_STATUS.md` не указывает этот этап как следующий разрешённый.
- Не выбирай библиотеку, облако, broker, cache, production platform, Secret Manager или real integration provider без явного решения.
- Зафиксированные initial versions: Spring Boot 4.1.0, Gradle Wrapper 9.6.1, Java toolchain 25. Upgrade выполняется отдельной maintenance-веткой после проверки compatibility.
- Не генерируй JPA entities или доменную модель из OpenAPI без отдельного архитектурного решения. OpenAPI по умолчанию задаёт транспортный контракт, а не модель хранения.
- Не создавай микросервисы без измеримой причины. Масштабируемость должна достигаться границами модулей, stateless-дизайном и понятными точками выделения.

## Качество

- Java 25, Gradle Kotlin DSL, reproducible build и dependency locking.
- Чистый, компактный и читаемый код; SOLID и DRY без догматизма.
- Паттерн применяется только для устранения конкретной сложности.
- Архитектурные границы проверяются автоматически.
- Доменные правила покрываются unit-тестами; инфраструктурные интеграции — тестами с реальными контейнерами.
- Миграции схемы обязательны; ручное изменение production-схемы запрещено.
- API и ошибки проектируются contract-first и соответствуют HTTP-семантике.
- Javadoc описывает публичные контракты, инварианты, причины и нетривиальные решения, а не пересказывает код.
- Каждое устойчивое решение оформляется ADR или обновлением проектной документации.
- `ENGINEERING_CHARTER.md`, `DECISION_REGISTER.md`, `IMPLEMENTATION_PLAN.md` и `PROJECT_STATUS.md` являются частью Definition of Done и обновляются в той же feature-ветке, что и соответствующее изменение.

## Git

- Сначала создаётся один чистый initial commit в `main`.
- После initial commit вся работа выполняется в короткоживущих feature-ветках.
- Один коммит — один законченный логический блок.
- Нельзя смешивать форматирование, рефакторинг и изменение поведения без необходимости.
- Перед коммитом обязательны применимые quality gates.
- История должна объяснять стратегию разработки и позволять безопасный откат.
- Коммиты и слияния выполняются только в рамках согласованного этапа.
